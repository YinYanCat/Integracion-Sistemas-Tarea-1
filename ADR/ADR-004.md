# **ADR-004 · Resiliencia y manejo de fallas de dependencia**

**Estado:** aceptada

**Contexto.** El servicio de dispensación depende síncronamente de la disponibilidad del servidor gRPC de stock para confirmar operaciones. Una caída de la dependencia no debe comprometer la estabilidad global del sistema REST.  

**Alternativas consideradas.**

- Opción A — Abierto a fallos: Permitir dispensar sin verificar stock si la red falla. Rompe las reglas de negocio, pero el sistema REST estará siempre disponible. 

- Opción B — Bloqueo indefinido: Esperar la respuesta del socket de red de forma ilimitada. Eventualmente se resolverán las peticiones, pero el periodo puede ser muy extenso y significa guardar todas las peticiones que no se hayan cumplido, lo que puede saturar los sistemas, eventualmente podría generar más problemas, como la caída de más servicios, ralentización de comunicaciones, etc. 

- Opción C — Timeouts estrictos y degradación controlada: Establecer un límite de espera y retornar un error RFC 7807 con estado HTTP 503. El reintento queda a cargo de quien consume la API, pues el sistema no reintentará automáticamente. 

**Decisión.** Implementar un timeout estricto de conexión en el cliente gRPC y capturar errores de tipo UNAVAILABLE o DEADLINE_EXCEEDED para retornar un error RFC 7807 con estado 503. 

**Justificación.** Protege al servidor REST frente a efectos en cascada y entrega una respuesta semánticamente precisa al operador. 

**Costo aceptado.** Intermitencias breves en la red, o que Stock esté momentáneamente lento sin estar caído, provocarán rechazos temporales de dispensaciones legítimas — el timeout no distingue entre ambos casos.

**Consecuencias.** El cliente externo de la API es responsable de decidir si reintenta tras un 503, y con qué espera entre reintentos. La caché Redis reduce indirectamente la exposición a este modo de falla: una lectura que sirve desde caché nunca dispara la llamada gRPC que podría fallar por timeout.
